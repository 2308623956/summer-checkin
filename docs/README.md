# Summer Checkin — 文档地图

> 这里是本项目的文档入口。**先读这张地图，再去读具体文档**，避免读到过时或不该读的内容。

## 1. 文档结构

```
docs/
├── README.md               ← 你在这里：文档地图与维护规则
├── PRD.md                  总产品需求文档（回答"做什么"，需求级；含每个需求的初步拆解）
└── tech/                   技术文档（回答"跨需求的稳定契约"）
    ├── README.md           技术文档索引 + PRD↔技术追溯表 + 已定事项
    ├── architecture.md     服务边界、认证、数据所有权、目录、硬规则、关键流程
    ├── backend.md          后端（service / FastAPI）：模块划分、函数清单、事务与幂等、agent 运行时
    ├── frontend.md         前端（web / Next.js）：路由表、页面职责与状态、组件复用、登录与令牌
    ├── integrations.md     第三方集成：模型池 / OSS / pgvector / 部署 / 环境变量
    ├── data-model/         数据模型（按域分册，含全部 31 张表字段与 Alembic 迁移）
    ├── api/                接口契约（总则 + 按模块分册，全部由 service 提供）
    └── decisions/          技术决策记录（ADR，一条一文件）
```

**任务级设计不放这里。** 一个需求的选型与详细设计写在 Trellis 任务目录 `.trellis/tasks/MM-DD-<slug>/` 里（`prd.md` / `design.md` / `implement.md`），按状态归档、按日期命名，完工后进 `archive/`。本目录只管**跨需求的稳定契约**与**需求本身**，这样加需求、改任务、归档任务都不需要动这张地图。

**分工线**：`PRD.md` 只回答"做什么"（用户、痛点、功能、范围、验收）；`tech/` 只回答"怎么做"（数据、接口、架构、依赖、选型）。同一个细节**只在一处写全**，另一处只写摘要并指向对方。

## 2. 每份文档管什么

| 文档 | 管什么 | 什么时候读它 |
|---|---|---|
| `PRD.md` | 目标用户、痛点、功能范围、优先级、验收标准、排期；1.6 每个需求的初步拆解，2.6 点明有哪些子系统 | 决定"要不要做、做到什么程度" |
| `tech/architecture.md` | 两个服务的边界与判据、认证、数据所有权、目录、硬规则、部署拓扑 | 动手写任何代码之前 |
| `tech/data-model/` | 31 张表的字段与关系、Alembic 迁移、保留与清理 | 改数据结构、写查询、做统计 |
| `tech/api/` | 接口总则、每个接口的职责与出入参 | 写前端调用或后端实现 |
| `tech/backend.md` | service 的模块与函数、事务与幂等、agent 运行时 | 写后端逻辑 |
| `tech/frontend.md` | 路由、页面职责、交互状态、组件复用、令牌传递 | 写页面与组件 |
| `tech/integrations.md` | 外部服务、环境变量、限额与超时、部署与 CI | 接第三方、部署、排查集成问题 |
| `tech/decisions/` | 每条技术决策的背景、选择、被否方案、代价 | 想改一个"看起来很简单"的设计之前 |
| `.trellis/tasks/*/` | 某一个需求的选型与详细设计（开工前写） | 开工前定方案时、复盘"当时为什么这么定"时 |

## 3. 维护规则

1. **单一事实来源**：一个事实只写一处。数据字段只在 `data-model/` 定义，接口只在 `api/` 定义；PRD 里出现的相关表格属于"方案概述"级摘要，详细版以技术文档为准。
2. **变更即更新**：改代码时同步改文档，按下表对应关系执行。

   | 改了什么 | 必须同步更新 |
   |---|---|
   | 数据库表 / 字段 / 迁移 | `tech/data-model/` |
   | 接口路径 / 出入参 / 错误码 | `tech/api/` |
   | 服务边界 / 认证方式 / 目录结构 | `tech/architecture.md` + `tech/decisions/`（新增 ADR） |
   | 页面 / 路由 / 交互状态 / 令牌传递 | `tech/frontend.md` |
   | 服务层模块或 agent 运行时 | `tech/backend.md` |
   | 环境变量 / 第三方服务 / 部署 | `tech/integrations.md` |
   | 功能范围 / 优先级 / 验收标准 / 排期 / 子系统归属 | `PRD.md`（并更新其"更新记录"表） |
   | 某需求的技术选型 | 该需求的 Trellis 任务 `design.md`；定稿后若成为跨需求契约，回写 `tech/` |

   **冲突优先级**：`tech/`（现状契约） > 任务 `design.md`（本任务方案） > `PRD.md`（需求摘要）。发现不一致就当场改，不留"以后统一"。

3. **先文档后代码**：新功能先改技术文档，再写实现；文档与代码不一致时，以"文档先改、代码跟进"为准。
4. **命名与版本**：文件名用英文小写加连字符；文档内用中文。PRD 用语义化版本（当前 `3.1.0`），ADR 用 `ADR-序号-短标题.md` 且一经记录不再改写（要改就新增一条并标注取代关系）。
5. **不写"历史的"内容**：文档描述**现在**要怎么做。已废弃的方案只在 `decisions/` 里作为"被否方案"留存一句话。
6. **任务产物不进 `docs/`**：`.trellis/tasks/` 按状态归档、目录名带创建日期，不适合当长期文档的锚点；跨需求要遵守的结论一律回写 `tech/`。
