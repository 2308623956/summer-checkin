# ADR-002 聊天室与 WS sidecar 不迁移

- 状态：已采纳
- 日期：2026-09-25
- 相关：`../../PRD.md` 1.5（Out-of-Scope）、`ADR-001-domain-service.md`

## 背景

参考项目里有一个全局单房间聊天室：前端是常驻悬浮按钮（`components/chatroom/chat-room.tsx`，由 `top-nav.tsx` 渲染），后端是独立 WebSocket sidecar（`server/`，默认端口 3001，Cookie 鉴权，含 `@AI` 机器人）。

PRD 已决定"聊天室先不开放、隐藏入口"。现在架构改成双服务（ADR-001），需要回答：聊天室和它的 sidecar 要不要跟着迁移？

## 决策

**不迁移**：新工程的 `web/` 不含聊天室页面与组件，仓库不含 `server/`，依赖里不含 `ws`。`chatmessage` 表保留在 Alembic 的初始 schema 里（表在、功能不启用），避免以后想恢复时再改一次基线。

## 被否方案

**A. 一起搬**：聊天室要跟着改成"数据从 service 出"，等于把一个非核心功能做两遍（页面 + 接口），而且它对本项目的两个目标（学习复盘闭环 / 后端架构能力）都没有贡献。

**B. 用 FastAPI WebSocket 重做**：技术上顺手，但长连接服务引入状态、扩容、鉴权续期等一整套问题，收益只是"有个实时功能"，不是本项目要证明的能力。

**C. 页面保留但关闭入口**（PRD 原方案）：在单栈时代这样最省；双服务之后，"保留页面"意味着 web 要为此多留一条到 service 的接口契约，成本反而比不搬更高。

## 代价与后果

- 少了一个可讲点（实时长连接 / 房间广播）。但 **AI 输出的流式响应仍在**（SSE / 流式），"流式 + 弱项评分"这条叙事不受影响。
- 若将来要做语音对练（PRD 附录 B 里被否的方向），需要另立一条 ADR 重新评估长连接方案——那时是另一个产品决策，不是本次的遗留问题。
- `chatmessage` 表空置，属于可接受的少量冗余。

## 验证方式

1. 新仓库依赖树里没有 `ws`；`web/src/components/` 下没有 `chatroom/`。
2. 页面导航与顶栏没有任何进入聊天室的入口。
3. `alembic upgrade head` 建出的 30 张表包含 `chatmessage`，且没有任何代码读写它。
